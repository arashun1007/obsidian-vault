# kaizen.md — 自動改善ループのランブック（三層リズム）

週次改善セッションの実行時・改善ループの初期設定時・月次棚卸しのとき読む。使用者が**「週次改善」「改善セッション」「改善回して」「今週の数字見て」**等と言ったら、他の作業より先にこのモジュールをロードし、§2を頭から実行する。前提知識は automation.md（信号色・5台帳・実験の安全ルール）。

## §0 思想 — 改善は「気が向いたとき」ではなくリズムで回す

- automation.md が「どこまで任せてよいか」の線引きと配管なら、このモジュールは**「どう回すか」の運転手順**。原則を知っていることと、毎週同じ品質で回せることは別物である。
- 人間に残すのは**裁定だけ**。検出・起草・記録・集計はAIの仕事。裁定に要る時間が週10分を超えたら、それはランブックの敗北なので提案の絞り込み（§2-4）を疑う。
- このループには二重構造がある。**Loop 1**=施策の改善（週次）。**Loop 2**=OS自体の改善（月次・§4）。Loop 2 があるから、回すほどOS正典が賢くなり、同じ失敗が二度提案されなくなる。

## §1 三層リズム

| 層 | 頻度 | 自動化 | 内容 |
|---|---|---|---|
| **日次** | 毎日 | 全自動（Green） | 数字の収集と台帳への記録。ガードレール監視——許容ラインを割った施策の自動停止+通知。人間は原則ノータッチ |
| **週次** | 週1固定 | 半自動（本丸） | 改善セッション（§2の8ステップ）。人間の仕事は5番の裁定のみ |
| **月次** | 月1（4週ごとでも可） | 半自動 | 棚卸しとLoop 2（§4）。勝ちパターンの昇格・失敗の焼き込み・ループ自体の点検 |

- 日次のガードレールは週次を待たない。**守りの自動化が常に先**（automation.md §1-3）。
- 週次の曜日・時刻は固定する。「今週は忙しいから飛ばす」が起こり得ない形（§5）にして初めてループと呼べる。

## §2 週次改善セッション — 8ステップ（この順で実行する）

**1. 台帳と健全性を読む。** 5台帳と接続状態を確認し、最初に**「実績がゼロだった」と「計測が壊れている」を区別**する（automation.md §1・計測パイプラインの状態語彙）。壊れた計測の上の分析はすべて砂上——計測の穴を見つけたら、それ自体を今週の提案の最上位に置く。

**2. 満了した実験を先に裁く。** 観測期間が終わった実験を、採用／巻き戻し／延長（理由必須）のいずれかに必ず落とす。宙吊りの持ち越しは禁止——「なんとなく続いている実験」は実験ではなく漂流である。判定は実験の安全ルール（automation.md §4）で行い、判定不能なら「何が欠けて判定不能か」を書いて計測修復を提案に回す。

**3. 異常と好調を検出する。** 前週比・ベースライン比で拾う。最小サンプル未満は「観測中」として提案対象から外す。同条件同士だけを比較する（automation.md §4）。

**4. 提案を起草する——上限3件。** 提案の型（仮説／対象／根拠／確信度／観測期間／許容ライン。automation.md §1-3）で書く。根拠には台帳の実数と出典（どのファイル・どの記録か）を必ず引き、根拠がなければ確信度は**勘**と正直に書く。10件出すAIの提案は1件も実行されない——3件を超えて見つけたら、残りは提案台帳に proposed で積んで翌週に回す。

**5. 人間の裁定。** 承認／却下／保留。**ここだけが人間の仕事**。裁定を急かさない。未裁定のまま翌週になったら保留として再掲し、3回連続保留になったものは「実質却下」として提案台帳へ戻す（理由欄=「3週保留」）。

**6. 承認分を装填する。** 承認された提案を実験台帳（提案台帳の状態遷移: proposed→approved→observing）に起票し、その許容ラインを日次ガードレールに登録する。Yellow該当（新しい訴求等）は、承認済みになったものだけを配信キューへ入れる。
装填時は**ベースライン確定ゲート**を通す: A/B等の比較実験は、開始前に同条件で十分な期間（目安2週間）のベースラインを取得し、**取得中は対象の条件を一切動かさない**。各腕の最小サンプル数と即時巻き戻しライン（ベースライン比の許容悪化幅）を実験カードに事前記入する。ベースラインなき実験は、結果が出ても比較基準がなく採否を判定できない。

**7. 判断ログへ追記する。** 追記のみ・書き換えない。**却下も理由つきで書く**——却下理由は、将来同じ提案が再浮上したとき毎回ゼロから検討し直さないための資産である。

**8. 週次ダイジェストを出力する。** 実測サマリー（出典つき）＋実験の状態一覧＋提案と裁定結果＋**人の所見一言**欄。所見のない数字はリサーチにならない（research-protocol.md）。

## §3 セッションの品質バー

- **データにない数字を1つでも創作したら、セッション全体が失敗**として扱う。数字には常に出典（ファイル・日付）を添える。
- **提案ゼロの週は正常。** 異常がなければ「異常なし」が正しい報告であり、ひねり出した提案は事故のもと。提案の空振り（却下）が続くより、正直な「今週は動かす根拠なし」のほうがループの信用を保つ。
- 出典のない「好調／不調」の形容は書かない。形容の前に数字、数字の前に出典。

## §4 月次棚卸し — Loop 2（掟への還流）

週次が施策を改善するのに対し、月次は**OSそのものを改善する**。この4項目を順に行う:

1. **勝ちパターンの昇格。** 採用された実験のうち、**別の素材・別の文脈で2回再現したもの**だけをOS正典の「勝ちパターン集」へ昇格する（1回の好結果は「有望」止まり: automation.md §4）。昇格時は適用条件と出典実験IDを添える——条件のない勝ちパターンは、文脈の違う場面で誤用されて死ぬ。
2. **失敗の焼き込み。** 巻き戻した実験は、理由つきで「やらないことリスト」（os-forge.md §6）へ写す。理由のない禁止は将来緩められて同じ事故を繰り返す。
3. **ループ自体の点検。** 空振り率（提案のうち却下された割合）・実験の平均滞留日数・計測の穴の残数を見る。空振り率が高い→検出基準が緩いか根拠が弱い。滞留が長い→観測期間の設計が長すぎるか、裁定が詰まっている。**ループの数字が悪いのに施策だけ責めるのは誤診**。
4. **正典の同期。** 現実とずれたOS正典の項目を現実に合わせて直す（os-forge.md §8）。書いてあるだけで運用されていない項目は「穴」に降格する。

## §5 自動起動の導入 — 人間が思い出さなくても回る形に

改善ループの完成形は、**セッションの開始すら人間がトリガーしない**状態である。導入は環境に合わせて:

1. **定期実行の仕組みがある環境**（Claude Codeのスケジュールタスク・cron等）: 週1回の固定時刻に「kaizen.md の週次改善セッションを実行」と投げる設定を作る。出力（ダイジェスト＋提案）は使用者が毎日見る場所（メール・チャット・所定のファイル）へ届ける。
2. **ない環境**: カレンダーの繰り返し予定＋「週次改善」と一言送る運用で構わない。ループの価値はトリガーの豪華さではなく、**毎週欠かさず回ること**から生まれる。

導入の掟:

- **初回は必ず手動で1周し、生成物（ダイジェスト・提案）を検品してから定期実行に昇格する。** 定義しただけの自動化は「穴」である（automation.md §5）。
- 自動起動の設定変更は使用者の確認を取ってから行う（SKILL.md 安全）。
- 2週連続でセッションの生成物が出ていなかったら、それは「改善が止まった」ではなく**「止まったことに誰も気づかない状態」**であり、最優先の修復対象。接続台帳の健全性欄にセッション自体の最終実行日を記録しておくと、この無音を検出できる。

## §6 立ち上げの最小形（P1で計測が回り始めた直後）

5台帳とガードレールが揃うのを待たずに始めてよい。最小形は:

```
週1回・固定曜日: ①手元にある数字を出典つきで並べる → ②提案を最大3件、提案の型で書く
→ ③人間が裁定 → ④判断ログ（テキストファイル1本でよい）に追記
```

これだけでもLoop 1は成立する。台帳の分化（os-forge.md §9）・日次ガードレール・自動起動は、回数を重ねながら足す。**完璧な装備を待ってループを始めないのは、柱7違反**（打席に立たない者は永遠に稼げない）。
