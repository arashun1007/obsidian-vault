# automation.md — 自動運転の設計（配信・計測・改善の3パイプライン）

自動化の設計・拡張のとき、およびP2（循環フェーズ）に到達したら読む。

## §0 思想 — マーケティングは「作業」ではなく「自動運転するOS」として建てる

このスキルの到達点は、うまい施策を打てる状態ではない。**寝ている間にコンテンツが配信され、数字が自動で集まり、週明けに改善提案が届いている状態**である。

- 人間に残す仕事は3つだけ: **原稿の魂**（実体験・信念・語り口）、**承認**（出してよいかの判断）、**判断**（価格・方針・実験の採否）。それ以外の反復作業——変換・配信・計測・集計・提案の下書き——はすべて自動化の対象。
- 柱3（基準値を狂気の一歩手前まで）は根性論ではない。**人力で維持できる基準値は基準値ではない。** 毎日の投稿・計測・振り返りは、仕組みに載せて初めて持続する。「今日は疲れたから投稿しない」が起こり得ない構造を作ることが、基準値の正体である。
- 柱4（自動化は時間の自由を買う手段）を忘れない。自動化の構築自体が趣味化して、売る打席（柱7）を後回しにしたら本末転倒——だからこそ段階導入（§6）を守る。

## §1 三本のパイプライン

### 1. 配信パイプライン（コンテンツ投稿の自動化）

```
在庫（ストック台帳）→ キュー → 定時実行（cron等）→ 投稿 → 実行ログ
```

- **在庫が主役**: 自動配信は「素材があること」が前提のシステム。シリーズごとの残弾数を台帳化し、閾値（例: 7日分）割れで補充アラート。**弾切れはエラーにならず無音になる**——だから能動監視が要る。
- **冪等がデフォルト**: 同じ投稿が二度出ない仕組み（投稿済みフラグ・実行ロック）を最初から入れる。二重投稿・二重配信は自動化への信頼を一撃で壊す。
- 投稿の中身は信号色（§2）に従う。キューに入るのは承認済みコンテンツだけ。
- 輪番設計・優先ルールは x-ops.md §2、メールの試し送り2段階は mail.md §5。

### 2. 計測パイプライン（分析の自動化）

```
日次収集（軽量取得）→ 正規化 → KPIツリーへ記録 → 週次ダイジェスト（自動集計 + 人の所見一言）
```

- **fail soft**: 計測は失敗しても本体を止めない。ただし失敗を隠さない——接続ごとに健全性ステータスを持つ: `正常` / `遅延（再試行中）` / `鮮度切れ` / `レート制限待ち` / `認証切れ` / `計測対象外（設計上取らない）` / `未接続` / `意図的停止`。
- この語彙が要る理由: **「投稿がなかった」と「データ取得が壊れた」を混同する**のが計測自動化の典型事故。数字ゼロの意味を状態で区別できないと、分析が全部砂上になる。
- 週次ダイジェストには必ず**人の所見を一言**書く欄を残す。所見のない数字はリサーチにならない（research-protocol.md §8）。自動化するのは集計であって、解釈の放棄ではない。

### 3. 改善パイプライン（改善の自動化）

```
気づき（数字の異常・好調）→ 提案（下書きはAI）→ 人間承認 → 実験 → 評価 → 採用 or 巻き戻し → 判断ログ
```

- 提案は必ず**提案の型**で書く: 仮説 / 対象 / 根拠（どの数字・どのリサーチ）/ 確信度 / 観測期間 / **許容ライン**（この数値がこれ以上悪化したら自動停止）。
- 許容ライン（ガードレール）は自動化してよい: 解約率・苦情・到達率が閾値を割ったら**施策を自動停止**するのはGreen（§2）。攻めの自動化より先に、守りの自動化を敷く。
- 評価の後は**採用か巻き戻しか**を必ず決めて判断ログ（os-forge.md §7）へ。「なんとなく続いている実験」は実験ではなく漂流である。
- 本節は原則。**実際に回す手順（週次セッションの8ステップ・月次のLoop 2・自動起動の導入）は kaizen.md**——原則を知っていることと毎週同じ品質で回せることは別物なので、運転は必ずランブックに従う。

## §2 信号色 — 自動化してよい範囲の線引き

| 色 | 範囲 | 例 |
|---|---|---|
| **Green（自動可）** | 外部に新しい主張を出さない反復作業 | 再同期・重複排除・欠損検出・計測リンク付与・承認済みキューの定時消化・投稿時刻や配分の提案・許容ライン違反時の自動停止 |
| **Yellow（人間承認必須）** | 外部状態を変える、または新しい訴求を出す | 新しい訴求文・強いCTA・誘導先の変更・投稿量の大幅変更・複数媒体への本格展開・公開/非公開/削除 |
| **Red（自動禁止）** | 魂と経営 | 原稿そのものの生成・改変 / 事実台帳の外にある効果・実績・証言・保証・比較の創作 / 価格・期限・希少性・予算・アカウント・ポリシーの変更 |

- 線引きを明文化する理由: 「便利だから」で越権自動化が一段ずつ進むのを防ぐ。**どこまで任せてよいかを毎回議論しないための憲法**であり、OS正典（os-forge.md）に転記して使う。
- Redは能力の問題ではなく信頼の問題。AIが価格を変えられないのではなく、**変えない**と決めることで、残り全部を安心して自動化できる。

### 信号色 × 自動化レベル（os-forge.md §2）の突合

二つの表は軸が違う。**信号色=権限（自動化してよい上限）**、**L1/L2/L3=実装段階（今どこまで自動か）**。混同せず、上限則で結びつける:

| 信号色 | 到達してよい上限 |
|---|---|
| Green | L1（全自動）まで可 |
| Yellow | **L2止まり**（起草は自動・実行は人間承認） |
| Red | **L3固定**（永久に手動） |

- 監査ルール: 自動化レベル監査（os-forge.md §2）で**L1にある項目は、信号色がGreenでなければならない**。YellowのままL1に上がっている項目は越権自動化——検出したら即L2へ降格し、判断ログに記録する。この突合を監査の必須チェックに含める。

## §3 五つの台帳 — 「集計画面」ではなく台帳運用がOSの本体

| 台帳 | 役割 |
|---|---|
| **接続台帳** | どの媒体と繋がっているか・データが最後にいつ届いたか・認証は生きているか |
| **指標台帳** | 各指標が何を意味し、どう数え、良い方向はどちらか（定義変更で版数を上げる） |
| **導線台帳** | 原稿→派生→媒体反応→リンク→商品ページ→購入までの一本道の記録 |
| **提案台帳** | 改善仮説の記録（§1-3の提案の型） |
| **判断ログ** | 提案→承認→実施→評価→採用/却下の履歴。**追記のみ・書き換えない** |

ダッシュボードは台帳の表示にすぎない。台帳なしに画面だけ作ると、「なぜあの時そう判断したか」が消え、同じ実験を何度も繰り返す。判断ログを追記専用にするのは、後から検証・監査できるようにするため。

## §4 実験の安全ルール

自動化された分析は、間違った結論も自動で量産する。以下を機械側の既定にする:

1. **同条件同士だけを比較する**（チャネル×コンテンツ種別×経過日数×観測期間を揃える）
2. **最小サンプル（目安30）未満は「観測中」**。勝敗を断定しない
3. **主指標が改善しても、守る数値（到達率・解約率・苦情）が悪化したら採用しない**
4. **1回の好結果は「有望」止まり**。別の素材でも再現して初めて勝ちパターンとして横展開する
5. **クリックは売上ではない**。注文・返金まで接続が取れるまで、収益指標を確定値として扱わない

## §5 設計原則（作る側の掟）

- **冪等がデフォルト**: すべての自動処理は二度走っても安全に。
- **定義しただけの自動化は「穴」に分類する**: スケジュール定義・スクリプト・設計書があっても、**初回実行の生成物を目視確認するまで、その自動化は存在しない扱い**にする（実例: 週次レポートのタスク定義があるのに出力ディレクトリ自体が空、というOSが実在した）。新しい自動化は必ず初回を手動トリガーで走らせ、生成物を検品してから監査表のL1に昇格させる。
- **fail closed と fail soft の使い分け**: リーガル監査・承認ゲートは fail closed（通らなければ止まる）。計測は fail soft（失敗しても本体を止めず、状態だけ残す）。逆にすると「監査をすり抜けて配信」か「計測エラーで配信停止」のどちらかの事故になる。
- **秘密は名前だけ設定に書き、値はgit外**（APIキー・トークン）。
- **最小工数の拡張を優先**: 新ダッシュボードをゼロから作らず、既存の画面にタイルを足す・集計を1本足す。自動化の建築が打席を圧迫し始めたら縮める。
- **API制約・規約適格の確認は設計段階で**: 設計→承認→コンテンツ量産まで進んだ後にプラットフォームの壁（文字数上限・書き込みAPI非対応・自動投稿ツールの規約不適格）に当たると、全部が巻き戻る。自動化の設計の最初の段で、対象プラットフォームの**公式ドキュメント**で最新のAPI仕様・利用資格・制限を確認する（実測: 投稿を量産した後にAPI制約が判明し、施策ごと見送りになった実事故がある）。
- **依存は一方向**: 各チャネルの自動化部品は共通の中核（台帳・契約）にだけ依存させ、部品同士を直接繋がない。1チャネルの仕様変更が全体を壊す構造を避ける。

## §6 段階導入 — 何から自動化するか

| フェーズ | 自動化の範囲 |
|---|---|
| P0 | **なし**。手で売る。自動化の検討自体が打席の回避になりやすい |
| P1 | **計測の自動収集から**（日次記録+週次ダイジェスト）。次に配信の予約投稿化。理由: 計測が先にないと、配信を自動化しても改善が回らない |
| P2 | 配信パイプラインの完成 → 改善パイプライン（提案→実験→判断ログ。運転手順=kaizen.md）→ ガードレールの自動停止と週次セッションの自動起動（kaizen.md §5） |

- 最初に自動化するのは「毎週必ずやる、判断の要らない退屈な作業」。判断の要る作業の自動化（Yellow領域）は、L2（起草→人間承認）の形でしか自動化しない。
- 自動化したら、自動化レベル監査（os-forge.md §2）のL1/L2欄を更新する。監査表と現実がずれたOSは信用できない。
