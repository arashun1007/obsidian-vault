# research-protocol.md — リサーチの型（宣言の根拠をつくる）

新施策の前・宣言の根拠づくり・数字が動かないときに読む。

大原則: **AIはリサーチを捏造しがちである。** ペルソナのでっち上げ、「市場調査によると」という無出典の断言、調べていないことを調べたフリ——これらはこのスキルにおける最重罪。**調べていないことは「未調査」と言い、根拠がない判断は「勘」と言う**（core.md §4）。

もう一つの大原則: **リサーチは打席の代わりにならない**（柱7）。調査が3週間続いて1回も売っていないなら、それは調査ではなく回避である。ディレクターは「打席警報」を出す。

## §1 リサーチメモの書式（全種共通）

```
■ リサーチメモ: <題名>
- 種類: 顧客/競合/市場/実売/自分
- 日付: <実施日>（鮮度期限: 種類別の目安 §7）
- 出典: <誰が・いつ・どこで。URL・発言者・場所>
- 生の声/生データ: <引用そのまま。要約しない>
- 解釈: <生データと明確に分離して書く>
- 次の一手: <この調査が支持する行動1つ>
```

生の声と解釈を分離するのは、後から解釈だけが独り歩きして「顧客がそう言っていた」に化けるのを防ぐため。

## §2 顧客リサーチ

- 源泉: リプライ・レビュー・DM・解約/離脱理由・コミュニティの投書箱（community.md §6）・購入直後アンケート。
- **実在する声だけを扱う。** ペルソナを作る場合は、実在の複数の声の合成であることを明記し、元の声への参照を残す。
- 集めるのは「言葉」。部族が自分の悩みを表現するときの語彙そのものが、コピー（lp-sales.md）の原材料になる。
- 罠: 声の大きい少数（1%層）の意見を全体と誤認する。声の主がラダーのどの段の顧客かを必ず記録する。

## §3 競合リサーチ（ファネル解剖）

- 競合の導線を実際に体験して分解する: 入口コンテンツ→リスト取得→教育→オファー→価格→購入後。各段の観察を記録する。
- 見るのは「何を売っているか」より**「どんな変化を約束し、どんな証拠を出しているか」**（positioning.md の三問で競合を分析する）。
- 価格・特典・保証は offer-design.md の裁定材料としてそのまま使う。
- 罠: 競合の真似は旗を失う近道。解剖の目的は模倣ではなく**空白の発見**（競合が約束していない変化・拾っていない部族）。

## §4 実売テスト — 最強のリサーチ

アンケートの「買いたい」は当てにならない。財布が開くかだけが真実。小さく売って学ぶ:

- **事前登録/ウェイトリスト**: 作る前に告知して登録数で需要を測る。登録ゼロなら作らずに済んだ——それが成果
- **プレオーダー/先行販売**: 完成前に少数へ販売。返金保証つきで実際に財布を開いてもらう
- **小ロット/限定枠**: 本命の前段として少人数枠で売り、提供しながら学ぶ
- 実売テストの結果（成約率・かけた声かけ数・断られた理由）は最高品質のリサーチメモになる。**断られた理由**は特に、オファーの証拠不足・価格・タイミングのどれが原因かを教えてくれる

## §5 市場・トレンドリサーチ

- Web調査で市場規模・トレンド・プラットフォーム動向を調べる。**必ず一次ソースまで遡り、URL と取得日を記録する。**
- 調査結果は**日付つきキャッシュ**として保存する。鮮度切れ（§7）のキャッシュで意思決定しない——「去年のトレンド」を信じて今年の施策を打つ事故を仕組みで防ぐ。
- プラットフォーム規約・法制度・料率は変わりやすい筆頭。年度依存の数値は使うたびに再確認する（事実の掟）。

## §6 自分リサーチ（柱1）

- 最重要顧客はまず自分。新商品・新施策の最初の調査対象は自分自身: 「自分はこれが欲しいか」「自分に効いたか」「自分は続けられたか」。
- 自分の変化の記録（ビフォーアフター・つまずき・かかった時間）は、捏造不可能な一次資料であり、コピーの証拠（lp-sales.md）として最強。
- 罠: 自分と部族の乖離。自分がもう初心者でない領域では、初心者だった頃の記録・現役初心者の声（§2）で補正する。

## §7 鮮度の目安

| 種類 | 鮮度期限の目安 |
|---|---|
| 顧客の声 | 1年（部族の語彙は移ろう） |
| 競合ファネル | 6ヶ月 |
| 市場・トレンド | 6ヶ月 |
| プラットフォーム規約・料率 | 1年、かつ重大変更の報道時 |
| 実売テスト | 商品・価格を変えたら失効 |

期限切れのメモを宣言の根拠に使うときは「（鮮度切れ）」を明記する。

## §8 計測は自動化されたリサーチ

- KPIツリー（os-forge.md §4）の計測結果は、毎週自動で届くリサーチメモである。週次で所見を一言書く習慣が、調査→宣言→制作→計測の循環を閉じる。
- 数字が動かないときの調査順序: ①計測が壊れていないか（データの死は施策の死と混同されやすい）→ ②ファネルのどの層で落ちているか（funnel.md）→ ③その層の顧客リサーチ（§2）へ。
